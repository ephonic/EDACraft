# M105 runtime evidence

Original report: `REPORT-PERF-original.md` (found at `~/vibe-coding/dsim-test/rtl-tests/perf-kit/REPORT-PERF.md`). Original workload inputs: `tests/perf_kit/inputs.json`. CPU/CRC/muldiv are the reported slow cases; AXI4 is the control. Cache VCS timing remains excluded.

Full workload timing uses fixed M104 and candidate generated C++ binaries plus freshly compiled VCS on mn02, all pinned to CPU 0, one warmup and three rotated rounds. Both GNU time CPU and elapsed wall medians are reported; compile time is excluded. Raw output and GNU time records are retained. VCS/DSIM numeric checksum comparison normalizes an existing `%08x` space/zero padding difference; DSIM baseline/candidate output comparison is byte-exact. No benchmark workload counts are reduced.

`baseline-profile.py` attributes a bounded active prefix using callgrind (not a performance result): CPU unary dispatch accounts for 7.20% inclusive instructions, CRC replication 12.04%, muldiv unary dispatch 11.81%. Inclusive percentages overlap other rows. DUT computations, driver/set and queue costs matter as well as TB waits.

`screen-candidate.py`, `paired-screen.py`, `screen-queues.py`, `screen-native.py` are provisional experiments, retained to distinguish rejected paths from the selected implementation. `measure.py` produces the final repeated full-workload report. Source archive, release identities, measured/generated C++ hashes and final figures are recorded after completion below.

All 48 timed/warmup runs completed and produced the same numeric end-to-end checksums, with identical workload counts. DSIM candidate stdout is byte-identical to M104. CPU still costs 3.70x VCS CPU time, CRC 1.74x, muldiv 1.98x. CRC wall time is close because VCS startup/other elapsed overhead matters; this is not evidence of equal engine throughput. The short AXI4 result is also strongly affected by startup. These are workload-specific measurements with waves disabled, not a universal simulator performance ratio. The shared server introduces variation; all three individual samples are retained in `measurement.json`, rather than choosing the best run.
