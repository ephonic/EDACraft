# M112：当前 RTL 单核热点分析

本轮只分析，不修改仿真器实现，不更换已发布的 M111 稳定版。结论是：应先检查连续赋值和端口传播形成的事件量、敏感项组织，以及逐语句预算维护；三个负载的侧重点不同。

## 采集方法与适用范围

- 实现冻结为 `12e798715da4b467bba25e6ae4badb747fa67659`，负载为原始完整 CPU、CRC、乘除法 RTL/TB，无波形，默认串行运行，103 的 CPU0，GCC 11.5 `-std=c++17 -O2 -pthread`。
- 增加 `-g` 后逐一核对 `.text`：三个程序的机器码与 M111 实测程序完全相同。`cpu_sample.c` 通过外部预加载库采集被 CPU 定时器中断的 PC，不在求值代码中插桩。各一次无采样控制运行，再轮换三轮采样，共九次完整运行、91449 个样本，所有完整输出均与原始基准一致。采样后符号化包含内联栈。
- 另用 `count.py` 在生成程序副本中插入诊断计数，完整运行三项负载并核对输出与计数守恒。该副本的耗时不用于性能结论。计数包括初始化；稳定输出、进程分类及逐信号明细在 `counts.json`。
- 重新解析 M111 的同一 200000000 tick 活动前缀 Callgrind，按函数聚合所有源文件的 exclusive Ir，独立核对总指令数。前缀指令归因与完整运行的 CPU 采样分别保留；callee inclusive 数字不相加。
- `collection.json` 保存全部采样/控制耗时、机器码和输出身份。未采硬件 PMU，未测 IPC、cache miss 或分支失误；软件定时器样本是近似 CPU 时间分布。仅一个控制轮次且共享机器未锁频，不由此计算采样器的精确开销或新增加速比。本轮没有重测门级/SDF，也没有采 VCS 内核，因此不把 dsim 热点直接换算成与 VCS 的逐项差额。

## 完整负载的 CPU 样本

以下按最外层符号归属，三行互不重叠。被内联的容器访问归入所在函数；被调用函数的样本归入被调用函数。

| exclusive CPU 样本 | CPU | CRC | 乘除法 |
| --- | ---: | ---: | ---: |
| `set_planes`：信号更新及通知 | 22.10% | 26.55% | 23.27% |
| `drive_planes`：驱动存储 | 6.73% | 2.91% | 4.19% |
| `run_to`：调度、队列、NBA 提交等 | 19.92% | 14.66% | 19.18% |

CPU 的 `assign_nba` 还占 6.31%，乘除法占 5.93%；CRC 的 NBA 入队被内联，不能用其独立符号缺席推断没有这项开销。CRC 的独立 `delay`/压堆符号合计 10.06%，乘除法为 8.18%；部分定时处理仍计在 `run_to` 内。

按最内层内联符号看，`step()` 分别占 **13.53% / 10.17% / 9.72%**，`std::function::operator()` 分别占 **6.20% / 3.55% / 5.48%**。这两个视图已包含在上述外层函数和生成过程之内，不能重复相加；它们指向逐语句计数/限额检查和过程分派成本。编译器的源行归属及指令布局会影响细分，实际可节省多少仍需独立实验。

前缀中 `set_planes` 的 exclusive 指令占比为 33.27% / 33.99% / 33.79%，明显高于其完整运行 CPU 样本占比。先前“约三分之一”的表述适用于指令，不能作为当前 CPU 耗时份额。

## 完整事件量揭示的问题

| 计数，单位：百万次 | CPU | CRC | 乘除法 |
| --- | ---: | ---: | ---: |
| 实际进程执行 | 472.50 | 99.49 | 306.09 |
| 信号写入 | 523.50 | 296.94 | 428.49 |
| 未改变值的写入 | 178.88 | 52.92 | 84.92 |
| 敏感项扫描 | 751.51 | 237.11 | 741.18 |
| 不在等待 / 订阅代次过期而跳过 | 234.00 | 137.62 | 407.49 |
| NBA 入队 | 118.50 | 24.64 | 163.20 |

### 1. CPU：大量细粒度连续赋值反复求值

**62.54%** 的进程执行为单次连续驱动求值，另有 **6.67%** 是简单复制桥接。分类由实际生成的过程体识别，规则见 `count.py`；这里的“连续驱动”是短过程中的单次 `drive`，不表示它已被证明可以安全融合。

一个具体例子：`tb.dut.stall` 写入 **13500016** 次，值只改变 **2** 次；`tb.dut.m_ldata` 写入 **12001041** 次，只改变 **2049** 次。全部写入的 **34.17%** 最终没有改变值。现有 `set` 确实已早退，但此前的过程唤醒、入队/出队、表达式读取及求值已经发生。

因此需要检查组合依赖粒度、编译期可知条件和求值区域，而不只是继续缩短 `set` 函数。未变化的写入数不能全部视为可删除事件：还须分析输入变化、四态、初始/同刻事件、观察点及执行预算。

### 2. CRC、乘除法：端口传播和过期敏感项

简单复制桥接占进程执行的 **44.67% / 39.01%**。例如乘除法的两条时钟复制过程，各运行 **55199013** 次，路径为 `tb.clk → tb.u_mul.clk` 和 `tb.clk → tb.u_div.clk`。它们引入了完整的过程唤醒、驱动及下游通知。

敏感项扫描中，因未等待或代次过期而跳过的比例为 CPU **31.14%**、CRC **58.04%**、乘除法 **54.98%**。乘除法 `tb.clk` 每次变化扫描 10 条记录，共 **551990130** 次；其中许多 TB 订阅属于其他等待位置。

当前缓存等待列表减少了重复注册/重挂成本，同时保留各等待位置的订阅；缓存命中后仍需要扫描和代次过滤。应检查活跃订阅的组织方式，以及满足语义条件的端口连接能否共享存储或减少转发任务。合法边沿不匹配另外计数，未混入上述“未等待/过期”比例。

### 3. 逐语句预算及通用过程状态

完整采样中约 10%–14% 的样本归属 `step()`。生成过程仍大量使用 `PC switch + step + get/set`；事件执行后又经过通用进程对象和 `std::function` 调用。这表明单纯把 Active 队列入口做一个批量循环，覆盖不到过程内部的逐语句维护、通用四态值构造和驱动/通知链。

可验证的下一项问题是：编译器能否对无挂起的基本块合并预算维护，临近限额时回到精确路径；以及能否扩大局部状态的直接访问范围。这里尚未实现变换或测得收益，不能直接删除预算检查。

### 4. CRC 的整数循环已经实际走了原生路径

完整运行 **10400000 / 10400000** 次原生循环 guard 均通过，共执行 **83200000** 次原生迭代。差距不能归因于这个 guard 持续失败。与此同时，无观察者的 automatic 函数槽仍有 **83200000** 次通用写入，原生循环外的参数、初值、结果和状态维护仍值得检查。这个数字表示访问次数，不是该部分的 CPU 耗时。

## 优先级与下一步判别

1. **CPU 先看组合事件量**：定位高频连续赋值为何反复产生相同值，选择一个可证明的依赖消减/求值区域实验，观察进程执行数是否实际下降。
2. **CRC、乘除法先看时钟传播及活跃订阅**：分别验证桥接任务和过期扫描能否减少，避免将两个候选合并后无法归因。
3. **跨负载检查生成过程的预算/状态维护**：以精确预算对照约束基本块处理；再评估 native 函数外围状态访问、NBA 存储与定时唤醒。
