# M131：当前 CPU 耗时原因复核

对**当前已发布 M130**重新采样。结论是：信号传播、逐过程执行边界及通用调度状态维护是明确的优先优化对象；不能把主要原因简单归为 TB 循环或整数计算。本轮为诊断，未修改生产代码，稳定入口保持 M130。

最近一次正式完整负载、相同 Intel 配置和 CPU25 的三轮中位 CPU 时间为 DSIM **8.94s**、VCS **5.89s**，比值 **1.52**；这些数字来自 [M130 正式测量](../m130-native-cases/README.md)，本轮带采样器的时间不作为新性能结论。

## 当前原生程序的耗时位置

103、CPU25、原始完整 7500006 周期 CPU 负载，DSIM/VCS 各一次无采样对照和三轮换序采样，八次完整输出均通过原始 PERF 检查。ITIMER_PROF 只记录当前 RIP，得到 DSIM **26517**、VCS **17002** 样本。以下均为相对 DSIM 全部样本的独占 PC 占比，不是相对 VCS 差距的比例，也不是可直接消除的耗时。

| 位置 | 占比 | 含义 |
|---|---:|---|
| 通用 `Sim::set` | 29.34% | 包含以下四项，不能重复相加 |
| ↳ 入口、索引检查、宽度归一化、变化比较 | 11.34% | 包括保存寄存器等入口成本 |
| ↳ 写入、订阅表入口和边沿解码 | 3.12% | 已变化值的发布准备 |
| ↳ 订阅扫描、等待/代数/边沿检查和入队 | 13.05% | 被调用函数的独占成本另计 |
| ↳ 返回路径 | 1.83% | 返回及恢复寄存器 |
| 叶批次共享入口及求值函数 | 13.74% | 包含有效 RTL 计算、等待重武装和批次管理 |
| `main` | 19.45% | 混合内联调度、NBA 提交等，不能全称队列开销 |
| `issue_comb_region` | 4.26% | 区域武装状态和队列请求 |
| `assign_nba` | 3.35% | 不包括后续 NBA 提交及 setter 的时间 |
| `delay` | 2.15% | 延时路径自身 |
| TB 时钟/激励两个闭包自身 | 3.00% | 不含共享运行时和下游 RTL 成本 |

完整派生结果和地址区间在 [analysis.json](analysis.json)，输入身份、各轮参数和输出哈希在 [collection.json](collection.json)。

本轮用 `-gline-tables-only` 重新编译诊断副本，确认其 `.text` 与被采样的正式模型**逐字节相同**，大小 `0x3bd90`、起址 `0x402460`，SHA256 均为 `8894ac936cb967bcea810e57daaa4d733391a0027ec94394ec40446855875578`，见 [debug-line-proof.json](debug-line-proof.json)。因此可以把正式模型的 PC 对应到诊断副本的内联行号；没有套用代码不同的调试构建。

`main` 中，`std::function` 调用处占全程序样本约2.87%，共享处理器调用处约1.21%，此外还有 Ready 弹出、过程状态、步数检查及 NBA 提交循环。调用处样本不包含被调函数，不能当作相应操作的总成本。DWARF 内联帧偶尔使用缩写 `_M_invoke`，所以函数独占总数仍使用原正式二进制符号；行号仅进一步定位。详细源位置见 `analysis.json/main_source_hints`，没有把混合的19.45%硬分成单一类别。

## 为什么编译掉更多 PC 后仍然慢

独立计数诊断运行固定200000000 tick前缀，保持 `PROFILE 200000000 5767258 1604582946171822610`，得到：

| 操作 | 次数 |
|---|---:|
| 信号读取 | 3903447 |
| setter 调用 | 1398727 |
| 实际变化 | 921690 |
| 订阅扫描（含区域） | 1704681 |
| 普通过程订阅扫描 | 1592680 |
| 因未等待/订阅代数过期而跳过 | 627083 |
| 单赋值 NBA 记录 | 316056 |
| 普通/叶/区域成员激活合计 | 1261646 |
| 剩余解释 PC 分派 | 436016 |

M129→M130 已将 PC 分派由1108667降到436016，减少60.67%，但同批正式 CPU 时间仅改善2.08%；全部发布以及 Ready 出入次数保持不变。过程内部执行已更直接，过程之间仍在反复执行通用发布、通知和队列路径。这支持把优化重心移到传播结构，不能再用 PC 减少比例预测整体加速。

34.11%的 setter 调用没有变化，39.37%的普通过程订阅扫描在未等待/过期检查后跳过；这些数字说明存在重复运行时工作，但正确性检查不能直接删去，也不能据此推算能节省多少秒。

## 与 VCS 的结构差别及下一步

本轮 VCS 原生程序身份仍为 `25645f9c29d6e2e6c4d6849eab668edaa6c228c8b21703c861fd15e7b51dffac`。其当前采样仍包含生成逻辑、调度函数和通知函数；VCS 也需要事件调度。此前对同一冻结默认原生库的 [直接检查](../m127-cpu-gap/README.md) 已确认：固定 NBA 目标先直接存储，再进入生成后继；部分组合传播在生成代码中连续计算，只在需要的边界请求排队。这与 DSIM 大量中间信号反复经过通用 watcher 和过程分派形成具体差别。不能从几个 VCS 代码块推导出整个仿真器的调度规则或精确差距分摊。

下一步应优先证明和编译纯组合依赖区域，减少中间发布与调度往返，随后让固定 NBA 提交衔接这些传播出口。观察点、延时、四态、动态等待、FIFO、预算中断及回滚必须保留边界/回退。规则依据 IR 和依赖语义，不依据 CPU 模块名、指令或测试数据。M128 已证明仅用静态回调替换订阅遍历会退化，本轮不建议重启该失败路线；单独加大批次而仍逐信号通用 set，也没有消除这里的主要工作。

## 复现和证据边界

在103的冻结输入目录运行：编译 `cpu_sample.c` 为 `cpu_sample.so`，`collect.py` → `symbolize.py`；独立执行 `count.py`。诊断行号副本的完整编译命令保存在 `debug-line-proof.json`；使用 `objcopy --dump-section .text=...`、`objdump -h -j .text` 验证相同后，运行 `symbolize-detailed.py ROOT` → `analyze.py ROOT`。

`analyze.py` 检查全部独占样本总数、setter 地址区间总数、main 总数及证明结果。软件计数覆盖固定前缀；采样覆盖完整负载。ITIMER_PROF 有时钟粒度与 PC 偏移，未获得硬件指令、缓存未命中或分支误预测计数；本轮没有用样本构造精确因果耗时模型。

自有模型/诊断程序、脚本、原始 PC/映射、日志、派生符号和原始 SV 输入归档并核对每个成员，见 [raw.json](raw.json)。归档镜像到本地和103的 `evidence/m131-cpu-cause/linux-raw.tar.gz`；不收录 VCS 二进制、生成源码或反汇编。不重新编译发布相同生产版本。
