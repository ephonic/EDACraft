# 完整 SDF 事件计数

对冻结 416 源实际生成的 scalar 完整程序做诊断副本插桩，未修改生产源码或用于 Linux 计时的二进制。macOS Clang C++17/O1 完整执行原网表、原 SDF、原测试平台的 128 笔输出，全部匹配既有参考。39 个计数器覆盖初始化及整个运行；`at_zero` 是首次正时间批处理前的快照。计数不是 CPU 采样、CPU 份额或 VCS 事件计数。

输入 C++ SHA256：`79dda7c6ed4045bdc0f0e2244fbb92c594c0275f3b4e50fbaa696baa2fc9d8b7`。插桩副本 SHA256：`6426c00249e878c3ab11be3c931d67c67f1cdc958e4ae0995a668cef4edc1964`。`instrument.py` 对 29 个替换锚点检查匹配次数，`check_instrumentation.py` 用手算序列验证队列、取消、复用和时间推进计数；`verify.py` 从原完整 C++ 重建变换、检查二进制/原始日志/128 输出并重算派生值，不重新运行仿真。

首次正时间前只有 1,860,891 次就绪入队，之后仍有 340,392,744 次，中间事件工作并非仅初始化。旧前缀 profile 中未等待 watcher 比例较高，本次 scalar 完整运行仅约 0.87%，不能用旧比例估算新后端的收益。所有正延迟交付都落在 2–255 tick；它支持尝试近时间桶加远时间堆，但不证明其他设计也有此分布。

优先方向为保持 FIFO/delta/step/取消及观察点的专用 SDF 作业、零延迟交付路径与定时队列。零延迟投递不能直接变成同步函数调用；移动 IOPATH 选择时刻也可能读到不同输入时间戳。尚未逐项量化这些机制相对 VCS 的耗时贡献。

原始数据：`run.stdout`、`run.stderr`、`results.json`；复查：`python3 validation/m5-sdf-event-profile/verify.py`。诊断计数与 Linux 首轮性能初筛分别独立运行，不能将此 O1 诊断的耗时用于性能对比。
